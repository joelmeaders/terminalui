# Maintaining the Storybook manual

Storybook is the component documentation entry point. Each of the 57 component pages has the same structure: setup, a working integration example, live controls, API reference, styling, accessibility, and states. The global framework selector changes setup and code for HTML/JS/CSS, Angular, Vue, and React. Its selection stays in Storybook globals and shareable URLs. The preview always renders the same Web Component.

## Sources of truth

- `.storybook/docs/catalog.ts` holds one usage guide and one example recipe per component. Include meaningful labels, realistic data, event payloads, limitations, and accessibility notes. A new catalog component without a guide fails validation.
- `.storybook/docs/examples.ts` converts each recipe to four framework examples. Imports, object properties, form bindings, custom events, and imperative openers are generated here. Do not keep four independent copies of every example.
- Component source JSDoc supplies API metadata through `scripts/metadata.mjs`. Keep `@slot`, `@fires`, `@csspart`, and `@cssprop` annotations on separate lines. The manifest includes inherited public APIs and excludes private or protected members.
- Give component CSS hooks a useful `@cssprop` description, including defaults and applicable limits. `docs/appearance.md` is the shared CSS property reference. The documentation check requires every public theme token and component CSS reference to appear in one of these sources, and rejects published private CSS properties.
- Give every custom event a typed `@fires` annotation, such as `@fires {CustomEvent<{ value: string }>} t-change - Selection changed.` Use `CustomEvent<null>` for an event without a payload. The manifest and React handler types share this declaration. The metadata build rejects missing custom event types.
- `docs/frameworks.md`, `docs/icons.md`, `docs/spinners.md`, `docs/slots.md`, and `docs/appearance.md` supply longer guides. The documentation page imports their contents directly. The Appearance introduction and each component's styling section reuse the appearance guide. Edit the original guide to update both repository and Storybook documentation.
- `.storybook/docs/ComponentDocs.tsx` supplies the shared page structure. `.storybook/docs/docs.css` supplies its appearance. Stories remain the source of live states and browser interaction tests.

The framework example is a complete starting recipe. Storybook Controls change the live preview, not that recipe. The page explains this distinction. React examples import each required wrapper from its component subpath and include a companion CSS block. The documentation check requires those selective imports. Angular setup explains the global theme import. Plain HTML examples use the standalone bundle and need no browser import map.

React examples read inferred custom event details directly. The installed-package check compiles `tests/types/react-events.tsx` against the packaged declarations. It checks public custom event contracts, native event types, compatibility with broad existing handlers, and agreement between the barrel and per-component wrappers. Browser integration checks cover actual React delivery, controlled selection, names, and keyboard focus.

The Typography foundation page uses `docs/typography.md` and `.storybook/docs/typography.ts`. Its one native HTML recipe supplies the preview and all four framework examples. `TypographyDocs.tsx` reuses the component manual's global framework selector. Typography has no custom element or fake catalog entry.

The Start here page derives its component count from the generated catalog. Its manual accessibility section displays setup, scenarios, a session record template, and unresolved review items from `docs/accessibility.md`. Edit that shared source to update both locations. Automated checks and manual results remain separate. The evidence table uses a named, keyboard-scrollable region at narrow widths.

## Validation

Run `npm run build`, then `npm run test:docs`. The check requires a guide and an autodocs story for every component. It checks example property names, custom events, and literal slot/part metadata. It compiles React TypeScript, Angular templates with AOT, and Vue single-file components with custom-element configuration. It then renders all 228 examples in Chromium and checks documented properties, input labels and values, imperative openers, and native typography styles and links. The Angular test harness loads the compiler for partially compiled dependencies; consumer Angular CLI builds use their normal linker. On narrow screens, the Storybook Controls table scrolls sideways within its named region. Keyboard users can focus that region and use the arrow keys.

Boolean controls use true/false radio groups with a programmatic group name. The group name stays visible at narrow widths. Arrow keys change the choice and update the live preview. This avoids an unlabeled switch in Storybook's built-in boolean control.

Run `npm run test:production` to check the built site. This covers every component documentation page and its page-level reflow at 320 CSS pixels, icon registration instructions, global framework selection across navigation and reload, keyboard access, and representative axe scans. Wide Controls and API tables scroll inside their own keyboard-reachable regions. The API reference shows an instruction at narrow widths; the Input manual test checks that ArrowRight scrolls its property table. The built-site check measures computed API and Controls table text contrast and column reachability across the component manuals. The Input manual also checks the category toggle's keyboard operation and visible focus. Review attached axe `incomplete` results; do not count them as passes. `npm run check` includes these checks and the existing component, story, package, and size gates.

After changing component metadata, rebuild before starting Storybook. Restart an already running Storybook development server if it retains an old manifest. Do not regenerate watched source or build metadata while development-server browser tests run.

These checks establish executable examples and representative browser behavior. A built-site test sets actual Chromium page zoom to 400% and checks page reflow across all 57 component manuals in each framework mode, including expanded Angular setup. It also checks ArrowRight scrolling in wide API and Controls table regions. A separate Input manual test checks framework selection at this zoom. Manual screen-reader review, visual review of the Controls table at real zoom, and complete WCAG conformance remain unproven. Track those checks in [accessibility evidence](accessibility.md).
